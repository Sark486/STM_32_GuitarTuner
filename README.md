# STM32 Guitar and Bass Tuner

A chromatic tuner for guitar and bass running on an STM32F411 "BlackPill" board. It listens through an I2S MEMS microphone, detects the pitch with the YIN algorithm and reports the nearest note and how far off it is in cents.

## Status: work in progress

What works today:

- Audio capture from an INMP441 microphone over I2S with DMA (32 kHz)
- Pitch detection from B0 (30.9 Hz, low string of a 5-string bass) up to about 1.4 kHz
- Conversion to note name and cents (A4 = 440 Hz)
- Output over UART, one line per reading

What is planned:

- **Display support.** An ST7789V SPI display with a proper tuner face. Until then the UART line is the only output.
- **ADC input.** A direct guitar jack input through an analog front end and the internal ADC, as an alternative to the microphone.
- Calibration and an accuracy table measured across the range
- Optional extras: adjustable A4 reference, guitar/bass/chromatic modes

The tuner shows the note name and cents only, without the octave.

## Output

The board prints a line whenever it has a confident reading, up to about 31 times per second:

```
Note:E,-2.41
Note:E,-1.87
Note:A,0.35
```

The first field is the note (sharps only: `C`, `C#`, ... `B`), the second is the offset in cents. Nothing is printed while there is silence or the reading is not confident enough.

Serial settings: 115200 baud, 8N1.

## Hardware

| Part | Notes |
| --- | --- |
| WeAct BlackPill STM32F411CEU6 | 100 MHz Cortex-M4F, 128 KB RAM, 512 KB flash, 25 MHz HSE |
| INMP441 I2S microphone | L/R pin tied to GND |
| ST-LINK V2 | Flashing and debugging over SWD |
| USB-UART adapter (CP2102 or similar) | Output and development tools |
| Logic analyzer (optional) | For timing measurements and checking the I2S and UART signals. I used the WeAct USB Logic Analyzer DLA Mini (24 MHz, 8 channels). |

### Wiring

| Board pin | Connects to | Function |
| --- | --- | --- |
| PB13 | INMP441 SCK | I2S2 clock |
| PB12 | INMP441 WS | I2S2 word select |
| PB15 | INMP441 SD | I2S2 data |
| PA2 | USB-UART RX | USART2 TX |
| PA3 | USB-UART TX | USART2 RX |
| PB6, PB7 | Logic analyzer (optional) | Timing markers, only with `TUNER_DEBUG_MARKS` |

The microphone also needs 3.3 V and GND. PC13 is the on-board LED and blinks if the firmware ends up in the error handler.

## How it works

1. I2S2 receives 24-bit samples at 32 kHz into a circular DMA buffer. Each half of the buffer holds 1024 samples (32 ms).
2. The main loop picks up each finished half and converts it to 16-bit samples.
3. A 119-tap FIR filter removes everything above 4 kHz, and the signal is decimated by 4 to 8 kHz.
4. YIN runs on the last 128 ms of the 8 kHz signal, once per 32 ms, and finds the period.
5. The period is refined on the original 32 kHz samples to get the accuracy back that decimation costs.
6. The frequency is converted to a note and cents, and printed if the confidence is good enough.

The firmware is a plain superloop without an RTOS. The DMA interrupt only sets a counter, and all processing happens in the main loop.

## Code layout

| Path | Contents |
| --- | --- |
| `Core/` | STM32CubeMX-generated code plus the HAL-dependent modules (microphone, capture, replay, UART retarget) |
| `lib/` | Portable C modules without any HAL dependency: `pitch` (decimator and YIN), `note` (frequency to note and cents), `level` (dBFS meter) |
| `tests/` | Host tests for the `lib/` modules, checked against golden vectors generated by the Python reference |
| `tools/` | Python tools for capturing, plotting, evaluating and generating test vectors |
| `data/` | Recorded and synthetic test signals, replay results and traces |
| `Drivers/` | ST HAL and CMSIS |

The same `lib/` sources are built twice: by `arm-none-eabi-gcc` for the firmware and by the PC's own compiler for the tests.

## Building

The project was developed in VS Code with the STM32CubeIDE for Visual Studio Code extension, and this is the easiest way to build it:

1. Install VS Code and the STM32CubeIDE for Visual Studio Code extension.
2. Open the repository folder and let the extension set up the project.
3. Select a CMake preset (`Release` for the normal tuner build) and build.
4. Connect the ST-LINK and start the `STM32Cube: Launch ST-Link GDB Server` debug configuration to flash and run.

### Command line

The same presets work without VS Code. This needs `arm-none-eabi-gcc`, CMake (3.22 or newer) and Ninja on the PATH, for example from [STM32CubeCLT](https://www.st.com/en/development-tools/stm32cubeclt.html).

```
cmake --preset Release
cmake --build --preset Release
```

The result is `build/Release/STM_32_GuitarTuner.elf`. Flash it with STM32CubeProgrammer or any other SWD tool.

### Presets

| Preset | Purpose |
| --- | --- |
| `Debug` | Debug build. The `lib/` modules are still optimized, otherwise pitch detection would not keep up with real time. |
| `Release` | The normal tuner build |
| `Release-capture` | Release plus the development tools (see below) and the timing marker pins |

### Development build

`Release-capture` turns on two CMake options:

- `TUNER_CAPTURE` adds a 1 s recording buffer (about 70 KB of RAM) and three single-character UART commands: `c` records and sends the samples to the PC, `u` uploads a recording from the PC, `r` runs the uploaded recording through the pitch module and reports the result and the CPU cycles of every step.
- `TUNER_DEBUG_MARKS` toggles PB6 and PB7 around the processing so the timing can be measured with a logic analyzer.

## Host tests

The portable modules are tested on the PC. The pitch module is compared stage by stage (decimator, difference function, normalized difference function, final result) with vectors produced by the Python reference implementation.

From the `tests/` folder:

```
cmake --preset host
cmake --build --preset host
ctest --preset host
```

This needs a native GCC or Clang and Ninja. On Windows, run it from the MSYS2 UCRT64 shell.

## Python tools

These tools were written mostly by AI, see [AI usage](#ai-usage).

Setup:

```
python -m venv .venv
.venv\Scripts\activate        # Windows
source .venv/bin/activate     # macOS, Linux
pip install -r requirements.txt
```

| Script | Purpose |
| --- | --- |
| `capture.py` | Trigger a recording on the board and save it as a WAV file |
| `plot.py` | Waveform, spectrum and spectrogram of a recording |
| `describe.py` | Harmonic balance, decay and pitch drift of a recording |
| `synth.py` | Generate synthetic test signals with exactly known pitch |
| `detectors.py`, `evaluate.py` | Run pitch detectors over the labeled recordings and score them |
| `pitch_ref.py` | Reference implementation of the pitch chain. The C module is checked against it. |
| `pitch_experiments.py` | The measurements behind the choice of detector and its settings |
| `make_vectors.py` | Export the golden test vectors and `lib/pitch/src/fir_taps.h` |
| `replay_compare.py` | Upload recordings to the board, run the firmware's pitch module on them and compare with the reference |
| `trace.py` | Log the board's result stream to a CSV file. It expects the `T,...` trace lines of an earlier firmware revision, which the current firmware does not print. |

Every script has a usage section in its docstring. `capture.py` and `replay_compare.py` need a `Release-capture` build on the board.
